# laqi v2 — Plan 3: Servidor MCP

**Estado:** ejecutado. Registro de lo construido.

**Spec:** [ADR-0006](/decisions/0006-mcp-server/),
[los tres escritores](/concepts/three-writers/).

## Qué entrega

`packages/mcp` y el comando `laqi mcp`, que lo sirve sobre stdio.

## La decisión de arquitectura: archivos, no HTTP

El servidor MCP **no habla con un laqi corriendo**. Opera directo sobre los
archivos del proyecto usando `@laqi/core`.

Se puede hacer porque el mock server lee el estado en cada request y el watcher
toma los cambios de archivo. Vale la pena porque un agente puede construir
mocks con laqi apagado, y funcionan cuando lo prendés — no hay que coordinar
dos procesos ni que el agente adivine en qué puerto está el servidor.

Cada llamada recarga desde disco: el panel, el editor web y el propio developer
escriben los mismos archivos, y una caché acá se desincronizaría al instante.

## Herramientas

| Herramienta       | Qué hace                                                              |
| ----------------- | --------------------------------------------------------------------- |
| `list_endpoints`  | Todos los endpoints, sus respuestas, y cuál está viva con qué capa    |
| `get_state`       | Escenario activo, overrides, y sólo los endpoints fuera de su default |
| `set_response`    | Fija la respuesta viva de un endpoint; `null` borra el override       |
| `set_scenario`    | Activa un escenario; `null` lo desactiva                              |
| `reset_state`     | Limpia overrides y escenario                                          |
| `create_endpoint` | Crea un endpoint y lo escribe al archivo                              |
| `update_endpoint` | Reemplaza la definición completa                                      |
| `delete_endpoint` | Lo borra, y limpia el override que apuntaba a él                      |
| `import_openapi`  | Genera mocks desde un documento OpenAPI 3.x                           |

El ADR listaba siete; se agregaron `delete_endpoint` (la corrección H8 que el
Plan 2a ya había hecho en HTTP) y `reset_state`.

### Las instrucciones enseñan el modelo de capas

El servidor manda instrucciones que explican qué es un id de endpoint y en qué
orden ganan las capas, con la regla de que un override le gana al escenario y
que para volver al default se usa `response: null` en vez de nombrarlo. Sin
eso el agente adivina, y adivina mal: escribir un override idéntico al default
deja el endpoint marcado como "cambiado" para siempre.

### Los errores vuelven como `isError`, no como excepción

Un agente tiene que poder leer el motivo y corregir. `set_response` con una
respuesta inexistente devuelve cuáles sí existen; un endpoint desconocido
devuelve la lista de ids conocidos.

## `import_openapi`

Convierte un documento OpenAPI 3.x en endpoints, generando cuerpos de ejemplo a
partir de los schemas.

- **Sólo JSON.** Traer un parser de YAML sería una dependencia grande para algo
  que el agente que llama puede convertir él mismo.
- **Nunca tira.** Lo que no puede convertir sale en `skipped` con el motivo. Un
  spec de cien rutas con dos raras vale más importado al 98% que rechazado
  entero.
- **No pisa nada por defecto.** Un endpoint que ya existe se reporta como
  skipped; hay que pedir `overwrite: true` explícitamente.
- Los nombres de respuesta salen del status (`200` → `ok`, `404` → `not-found`,
  `500` → `error`), no del número: un agente pide `boom`, no `status-500`.
- El default es el 2xx más bajo — el camino feliz.
- Maneja `$ref` circulares (normales en specs reales), mezcla `allOf`, respeta
  `example` / `default` / `enum` / `format`, y saltea las claves de rango
  (`2XX`, `default`) que OpenAPI permite pero no son un status concreto.

## Tres agujeros de validación que se cerraron

El ADR advertía: «un agente con estas herramientas puede escribir archivos del
proyecto. Debe estar acotado estrictamente al directorio de mocks — nunca
fuera». Al construirlo aparecieron tres huecos reales:

1. **`writer.ts` no contenía las escrituras.** `join(root, file)` deja que
   `'../x.json'` salga del proyecto. Ahora todo escritor pasa por una guarda
   que resuelve y se niega si el resultado sale de la raíz. **No era teórico:**
   la primera corrida de esos tests, antes de la guarda, dejó un `escaped.json`
   en el tmpdir compartido de la máquina.
2. **`Project.createEndpoint` escribía antes de validar.** Un agente creando
   `/__laqi/...` recibía `ok` y un archivo de mocks que después fallaba al
   cargar. Ahora valida con el mismo `parseEndpointKey` que usa el loader,
   antes de tocar el disco.
3. **`parseEndpointKey` aceptaba segmentos `..`.** Una URL se normaliza antes
   de rutear, así que esa ruta no se puede alcanzar nunca: era un endpoint
   muerto escrito en silencio en el archivo del usuario. Ahora es un error
   explícito.

Los tres arreglos son en `packages/core` y `packages/schema`, así que
benefician también al control plane y al editor.

## Verificación

- **62 tests** del paquete, **14 de ellos manejando el servidor real sobre
  stdio real** con el cliente del SDK de MCP — se spawnea `bun apps/cli mcp` en
  un directorio temporal y se habla el protocolo de verdad.
- 358 tests en total en el repo, `check-types` y `lint` limpios.

## Fuera del alcance

- **YAML** en `import_openapi` (ver arriba).
- **Templating** (`{{uuid}}`) sigue sin plan asignado.
- El servidor MCP **no expone el log de requests en vivo**: es un stream, y las
  herramientas MCP son request/response. Un `recent_requests` con buffer sería
  el diseño, pero requiere hablar con el proceso servidor — justo el acople que
  este plan evita a propósito.
