# ADR-0009 — No i18n: English everywhere, and why

**Status:** Accepted
**Date:** 2026-08-27

## Context

laqi has two user-facing surfaces: the CLI (terminal output, error messages)
and the web panel at `/__laqi`. The author is a Spanish speaker, and the
question came up of whether either surface should be translated, or should
support several languages.

This ADR exists so the analysis is not repeated. The conclusion is not
obvious in the abstract — it becomes obvious once you count what would
actually be translated.

## Decision

**English everywhere. No i18n infrastructure in the CLI or the panel.**

This also settles the project's writing language: code comments, commit
messages, PR titles and bodies, and documentation are written in English.

## Why not the CLI

**Error messages get pasted into search engines, GitHub issues and LLMs.**
There are around sixty error strings in the codebase, and they are written
carefully — they name the file, the line and the cause. A developer who gets

```
duplicate route GET /users declared in laqi/api.json:2 and laqi/api.json:13.
Neither is served — remove or rename one.
```

pastes it verbatim and finds other people with the same problem. Translate it
and they are alone with it.

Localising a developer tool's error messages makes the user's life **worse**.
This is one of the few areas where English is a utility rather than a default.

Two supporting reasons:

- The CLI's other main consumer is a coding agent, through `laqi mcp` or by
  reading terminal output. English is the lingua franca of tooling and agents
  handle it natively.
- Developer tooling is overwhelmingly English. A Spanish CLI reads as amateur
  rather than as welcoming.

## Why not the panel

The counting is what settles it. The panel has **roughly fifteen strings of
translatable prose** — `Filter`, `Requests`, `Pause`, `Clear`, `Retry`,
`Sign out`, `Add`, `Save to file`, and a handful of help sentences.

Everything else on screen is vocabulary that does not translate:

```
GET  POST  PUT  PATCH  DELETE  OPTIONS
default  state  scenario  header
endpoint  status  delay  curl  JSON
X-Laqi-Resolved   /__laqi/api/state
```

It is HTTP jargon and laqi's own proper nouns. Translating the fifteen strings
produces a **half-Spanish, half-English interface** — "Filtrar por método,
path, descripción o response name" — which reads worse than the consistent
English one.

And the cost is not translating fifteen strings. It is the machinery: an i18n
library, locale detection, translation files, and the standing tax that every
future string needs a key. For fifteen sentences surrounded by jargon that
stays in English regardless.

## When this should be revisited

So this is a decision rather than a dismissal — **revisit it if the panel's
audience stops being the same developer who runs the CLI.** If it is ever put
in front of QA, designers, or a non-technical client, the vocabulary stops
being purely technical and the arithmetic changes.

Today both surfaces have exactly the same audience.

## What is worth doing instead

If the goal is "let more people use this", **accessibility is where the
effort pays off**, not internationalisation. The panel has a reasonable base
— chips carry `aria-pressed`, inputs carry `aria-label`, there is a visible
focus ring, and the sharing band respects `prefers-reduced-motion` — but it
has never been audited. Known gaps:

- The ⌘K palette has no dialog focus management: it does not trap tab, and it
  does not restore focus on close.
- The live request log has no `aria-live`, so a screen reader never announces
  arriving requests.
- The neon accents on `#0B0A0F` were assumed to pass contrast, never measured.
  The design spec itself warns against body copy in `--mint` at weight 300.
- The layer markers are 5px coloured squares: **information encoded in colour
  alone**, a classic WCAG failure.

That has a real audience, it is bounded, and it is a quality signal.

## Consequences

**In favour:**

- No i18n machinery to build, test or maintain.
- Error messages stay searchable, which is their most valuable property.
- One consistent voice across CLI, panel and docs.

**Against:**

- Spanish-speaking users read an English interface. In practice they already
  do, for every other developer tool they use.
- The pre-existing Spanish documentation (ADRs 0001–0008, `analisis-v1`,
  `conceptos`, `diseno`) is now inconsistent with the project default. It is
  left as it is: it is the author's own writing and rewriting it buys nothing.
  Everything new is written in English.
